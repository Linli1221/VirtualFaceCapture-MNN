# M1：自适应抖动缓冲（手机 500 ms 发送缓冲迁移到 PC）

> **rawTrackV1 增量（P1）**：raw 推流连接的 raw_track 二进制帧**旁路手机端本缓冲**
> （[`raw-track-protocol.md`](./raw-track-protocol.md) §2.5）——帧序由 facecapture-sdk 的
> FrameReorderBuffer 保障、延迟与播放控制全部归 Windows 的 500 ms playout。per-client
> 发送队列（§8）的 control 保序规则原样适用于二进制条目（hello / ack / bye / pong 绝不被
> raw 帧挤掉或乱序）。本页的 500 ms 缓冲只服务文本 track / calib（legacy / v1 文本路径）。

> 目标：端到端延迟从约 0.58 s 降到良好网络下 < 200 ms，同时在网络抖动时保持稳定。
> 不改变手机推理链路，不改协议已有字段语义（只做纯增量扩展）。

## 1. 两步实施与开关

| 步骤 | 内容 | 开关 | 状态 |
|------|------|------|------|
| 第一步 | PC 侧自适应 jitter buffer 上线，手机**仍保留 500 ms** 发送缓冲。验证 PC 新逻辑正确，且 PC 深度稳定在 80~150 ms，**不叠加成 1 s**（总计 ≈ 0.65 s） | PC：`jitterBufferV1`（默认开，`?jb=0` 回退旧逻辑） | 已实现 |
| 第二步 | 手机新增配置 `send.bufferMs`，允许设 0（算完即发）；经 hello 协商，**只有 PC 声明支持 `jitterBufferV1` 时才允许手机用 0** | 手机：`send.bufferMs`（500 = 第一步模式，0 = 低延迟模式） | 已实现 |

回滚路径（两步都能退）：

- PC 回退：URL 加 `?jb=0`（或把 `JITTER_BUFFER_ENABLED` 关掉）。此时 PC 不在 hello 里声明 `jitterBufferV1`，
  手机即使配置了 `send.bufferMs=0` 也会回落到 500 ms 缓冲；PC 延迟逻辑退回旧版（快速输入延迟为 0）。
- 手机回退：`send.bufferMs` 改回 500（或任意 ≥100 的值）。`TrackingFrameBuffer` 的代码**原样保留**，
  配置 0 只是让 `dispatch()` 旁路它，随时可切回。

## 2. 职责边界：jitter buffer 与 ParamTimeline

**没有第二套缓冲层，两层延迟不会相加。** jitter buffer 就是 ParamTimeline 内部的「延迟控制器」：

```
┌─ jitter buffer（自适应缓冲深度控制器，interp.js 的 delayMs / primed 部分）────────┐
│ 决定「渲染时刻应落后输入时间轴多少」：                                            │
│  · 起播预缓冲（primed）与断流后重新预缓冲；                                      │
│  · 深度目标分档：稳定 80~150 ms / 抖动 200~300 ms / 剧烈 400~500 ms；            │
│  · 依据：输入间隔 p85/p95、连续大间隔次数、seq 跳变次数、缓冲见底次数、          │
│    传输滞后抖动（p90−p10）——全部用分位数，不用最大值；                          │
│  · 快升慢降 + 变化限速 + 档位迟滞（保证 sampleAt 单调、绝不倒带）；              │
│  · 见底 / 溢出统计。它不持有报文队列，只输出一个 delayMs。                       │
└─────────────────────────────────────────────────────────────────────────────────┘
                                  │ delayMs（唯一的缓冲深度输出）
                                  ▼
┌─ ParamTimeline（播放时间轴，interp.js 的 samples / push / sample 部分）──────────┐
│ 决定「给定播放时刻，参数应该是什么」：                                            │
│  · 样本存储（track.t + 时钟偏移 → 媒体时间轴）与线性插值；                       │
│  · 时钟偏移估计（最近 12 帧「到达−采集」最小值，逐帧 ≤1 ms 小步跟随）；          │
│  · 断流外推上限（≤40 ms 且 ≤0.75 个输入间隔）与乱序丢弃。                       │
│  它不决定延迟多少，只消费 jitter buffer 给出的 delayMs。                          │
└─────────────────────────────────────────────────────────────────────────────────┘
```

两层共用同一条时间轴：`sampleAt = now − delayMs`，在同一批 samples 上插值 —— **不存在第二条队列**，
所以叠加 500 ms（手机）+ 500 ms（PC）这类双重缓冲不可能发生；PC 深度上限硬编码为 500 ms。

## 3. 时间基准与单调性

- 时间基准优先用 `track.t`（手机采集时间），沿用「最近 12 帧（`offsetWindow`）到达−采集的**最小值**」
  估计时钟偏移（网络只会加延迟，最小值最接近真实偏移）；偏移每帧最多跟随 1 ms（`offsetStepMs`），
  突变 >120 ms（`offsetJumpMs`）时重新锚定。
- `sampleAt` 单调保护（`_lastSampleAt`）：无论延迟怎么变，播放时刻只前进不后退 —— **绝不倒带**。
- 无 `track.t` 时退化为按到达时间排队（旧行为不变）。

## 4. 缓冲深度自适应

| 档位 | 深度 | 触发信号（任一） |
|------|------|------------------|
| 稳定 | 80~150 ms | 无大间隔、无 seq 跳变、无见底、传输滞后抖动 < 40 ms、间隔抖动 < 40 ms |
| 抖动 | 200~300 ms | 偶发大间隔 / 2 s 内有 seq 跳变或见底 / 滞后抖动 ≥ 40 ms / 间隔 p95−p50 ≥ 40 ms |
| 剧烈 | 400~500 ms | **连续 ≥3 次大间隔** / 2 s 内 ≥3 次 seq 跳变 / 2 s 内 ≥3 次见底 / 滞后抖动 ≥ 150 ms / 间隔抖动 ≥ 120 ms |

- 档内深度 = `clamp(输入间隔 p85 + 传输滞后 p95 + 8 ms 余量, 档位下限, 档位上限)` —— **分位数估计，不用最大值**。
- **快升慢降**：上升 τ=100 ms、限速 0.6 ms/ms（抖动一出现立即加深，加深瞬间播放最多短暂放慢到 40% 速度）；
  下降 τ=2.5 s、限速 0.1 ms/ms（稳定后慢慢收回）。
- **档位迟滞**：升档立即、降档要保持 2 s —— 信号在阈值附近抖动时深度目标不会 200↔400 来回横跳。
- 大间隔判定：`dt > max(80 ms, 2 × 最近窗口最慢节奏)`。均匀慢输入（如稳定 5 fps）不算抖动；
  若输入本身慢到档位上限盖不住真实需要，深度逃逸到 `min(base, 500 ms)`，避免系统性饿肚子。

## 5. 起播、见底、溢出、断流恢复

- **起播预缓冲**：内容攒够一个缓冲深度（或 800 ms 超时兜底）才开始推进播放；预缓冲期间保持**首帧**，
  不是「最后一帧」，起播不产生回跳。onopen / onhello / 断线重连 / 手机时钟重锚都重新预缓冲。
- **见底**：外推上限沿用原约束 —— ≤40 ms 且 ≤0.75 个输入间隔；外推期间记 `starvedFrames / starvedEpisodes`，
  进入 2 s 窗口参与分档（见底是深度不够的直接证据）。
- **溢出保护**：jitter 模式样本上限 64 条（旧模式 12 条），到顶丢最旧；延迟硬上限 500 ms，不会滚雪球。
- **断流 2 s 再恢复**：`dt > 250 ms` 视为断流，清空样本、重新预缓冲；新段时间轴只向前，
  `sampleAt` 单调保护保证不倒带；恢复后从新帧继续插值，**不冻结在最后一帧**（有 selftest 用例覆盖）。

## 6. seq、calib/track 顺序

- seq 去重沿用 app.js `handleMessage` 的「seq ≤ lastSeq 丢弃」；seq **跳变**（缺帧）会被
  ParamTimeline 记入 2 s 窗口作为拥塞信号。onopen / onhello 把 `lastSeq` 复位为 −1（协议 §7.3）。
- **calib 与 track 的相对顺序**：
  - 手机缓冲开启（`send.bufferMs>0`）：calib 与 track 走同一个 FIFO（TrackingFrameBuffer），
    顺序天然保持；
  - 手机缓冲旁路（`=0`）：calib 与 track 走**同一个 per-client 有序发送队列**（见 §8），
    calib 不会被提前/滞后于相邻 track；
  - PC 侧：calib 在 `onCalib` 同步处理（mapper 复位），track 走时间轴 —— 顺序错配会表现为
    「校准瞬间模型姿态跳一下」，由上面两条保证不会发生。

## 7. hello 协商（协议纯增量）

PC 在 WS 建连后立即发（老手机把未知 type 忽略，完全兼容）：

```json
{"type":"hello","protocol":"vfc-tracker","version":1,"features":["jitterBufferV1"],"t":1730000000000}
```

手机端生效缓冲规则：

- `send.bufferMs > 0` → 用配置值（第一步验证模式）；
- `send.bufferMs == 0` → **仅当当前所有已连接客户端都声明 `jitterBufferV1`** 时才为 0；
  任一客户端没声明（含老 PC）→ 回落 500 ms 并记日志，新客户端连入/断开时重算；
- PC `?jb=0` 时不声明该特性 —— 手机自动保留 500 ms，回滚闭环。

## 8. 手机端：send.bufferMs=0 的行为与 pendingTrack 覆盖语义

### 8.1 退化行为

`send.bufferMs=0` 时 `dispatch()` 旁路 `TrackingFrameBuffer`（类代码原样保留，可回滚），
算完即发。`TrackingFrameBuffer` 的溢出保护（`maxQueued` 丢最旧）对应到 per-client 队列的
上限丢弃（见下），仍然存在。

### 8.2 问题：pendingTrack 的「最新帧覆盖写入」

现状 `TrackingWsConnection.pendingTrack` 是单槽 `AtomicReference`（新帧覆盖旧帧）。关闭手机缓冲后：

1. **中间帧会被覆盖**：发送节奏 = 生产节奏（突发），writer 稍慢（哪怕只是上一帧还在 TCP write）
   就会把中间帧挤掉。缓冲开启时放行是匀速的、覆盖只发生在网络跟不上时；关闭后连健康网络都
   可能突发丢帧，PC 时间轴只能靠插值补洞。
2. **更严重：calib/track 顺序反转**：calib 走 controlQueue（writer 优先发送），track 走槽位。
   若某帧 track（采集早于 calib）先占槽位，calib 先被发出、该帧 track 随后才发 —— 顺序反了；
   PC 若在 calib 处理后还收到校准前的 track，校准基线与数据错配。

### 8.3 方案：per-client 有序发送队列（已实现）

- track 与 control（hello/calib/pong/ack/bye）进**同一个 FIFO**，严格保序（修复顺序反转）；
- 上限（约 8 条 track + 32 条 control）；溢出时**丢最旧的 track**（绝不丢 control），
  全是 control 时丢最旧 control 兜底 —— 延迟有上限、内存有界；
- **慢客户端不拖慢推理线程**这一原则继续保持：
  - `offerTrack/offerControl` 只做一次有界队列操作（非阻塞、不碰网络 IO），推理线程投递即返回；
  - 真正的网络写只发生在每连接独立的 writer 线程；TCP 背压只让 writer 阻塞，
    反压到队列上限即丢最旧 track（延迟封顶），绝不回传到推理线程；
  - 与旧单槽方案相比：慢客户端的代价从「永远只发最新帧」变为「最多积压 8 帧（≈130 ms @60fps）
    后丢旧帧」——用有界的小 FIFO 换来 calib/track 顺序正确，延迟仍然有界。
- 对应的溢出保护语义与 `TrackingFrameBuffer.maxQueued` 一致：**延迟有上限比一帧不漏更重要**。

## 9. 验收清单与测量方法

> 以下为**测量方法**，不含编造的实测值。自测（`windows-client/tools/selftest.js`）中的数值
> 是仿真验证（注入抖动 / 断流的确定性模拟），不是真机实测。

### 9.1 良好局域网：端到端延迟 < 200 ms

- **方法 A（真全链路，推荐）**：手机摄像头对准另一台设备播放的毫秒计时器画面（或网页秒表），
  PC 侧对 Live2D 窗口以 60 fps 录屏 30 s；逐帧读出「录屏帧时刻」与「计时器显示值」之差，
  即**相机曝光 → PC 上屏**的端到端延迟。取 p50/p95（不用最大值）。重复 3 次取中位数。
- **方法 B（软件口径，含采集→写参数）**：PC 调试面板（D 键）读 `interp.delayMs` 与
  `latencyMs`（ping/pong RTT）；软件口径 ≈ `delayMs + RTT/2 + 推理耗时（手机端日志）`。
  更精确的做法是在 `__vfcDebug` 里记录 `performance.now() − (track.t + stampBase)` 的 p50/p95
  （`stampBase` 就是 interp.js 的时钟偏移估计），它覆盖「手机采集 → PC 参数写入」。
- 口径说明：<200 ms 目标对应：推理 ≈15-30 ms + 网络 ≈2-10 ms + PC 缓冲 80~150 ms + 渲染 ≤17 ms。
  第一步（手机仍 500 ms）预期 ≈0.65 s，用于验证「不叠加成 1 s」。

### 9.2 人为注入 100 ms 抖动：不出现可见卡顿

- 注入工具：Windows 用 [clumsy](https://jagt.github.io/clumsy/)（LAG/抖动模型），
  Linux 用 `tc netem delay 30ms 100ms distribution normal`，作用在手机→PC 的局域网路径。
- 观察口径：
  - 调试面板「缓冲档位」应进入**抖动**（或剧烈），`插值延迟` ≥ 200 ms；
  - 「见底」次数应接近 0（selftest 口径 < 5%）；
  - 录屏肉眼无可卡顿/倒退；必要时逐帧读参数值，步进应绝大多数帧在正常节奏（0.4~0.6），
    允许加深瞬间短暂放慢，**绝不允许负步进（倒带）**。

### 9.3 人为断流 2 s 再恢复：重新 primed、不倒带、不冻结在最后一帧

- 注入：clumsy 断链 2 s / 手机关 Wi-Fi 2 s 再开 / mock-tracker 暂停 2 s。
- 观察口径：
  - 断流期间：模型外推 ≤40 ms 后保持（允许停住，无数据是物理事实）；
  - 恢复后：调试面板 `primed` 先 false（重新预缓冲）再 true；seq 恢复递增；
  - 录屏中模型恢复跟随动作，**没有回跳（倒带）也没有永久冻结**；
  - selftest「断流 2 s 再恢复」用例对上述三条均有断言。

## 10. 自测覆盖（windows-client/tools/selftest.js）

jitterBufferV1 相关用例（全部通过；旧有 87 项行为回归全绿）：

1. 起播预缓冲：攒够一个深度才起播，预缓冲期间保持首帧（不倒带）；
2. 稳定局域网（手机仍 500 ms、PC 输入均匀）：深度稳定档 80~150 ms，**不叠加成 1 s**；
3. 注入 100 ms 到达抖动：升到抖动档 ≈200 ms，播放无可见卡顿（步进均匀）；
4. 剧烈抖动（到达抖动 0~300 ms）：深度 ≥250 ms，不倒退、不跳变；
5. 连续大间隔 ≥3 次（生产端卡顿）：判剧烈档，目标深度 400~500 ms；
6. seq 跳变：2 s 内连续跳变判剧烈档；
7. 断流 2 s 再恢复：重新预缓冲、不倒带、不冻结在最后一帧；
8. 断流外推上限：≤40 ms 且 ≤0.75 个输入间隔（沿用原约束）；
9. 溢出保护：样本上限到顶丢最旧，延迟不滚雪球；
10. 快升慢降：抖动出现立即加深，稳定后缓慢收回。
